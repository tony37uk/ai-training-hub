Multi-Agent Systems & Swarms Explained

⏱️ 20 min read 🟡 Intermediate 🧠 Concepts, no coding

One agent can do a lot. But some jobs are too big, too broad or too varied for a single agent working through them one step at a time. A multi-agent system splits the work across several specialised agents. When people talk about agent "swarms", this is what they mean.

💡 New to agents? Read Getting Started with AI Agents first. This guide builds on the Reason–Act–Observe loop explained there.

What Is a Multi-Agent System?

Instead of one agent doing everything, several agents each take a role, such as researcher, writer or reviewer. Each agent has its own instructions, its own tools and, importantly, its own context window, so it can focus on its piece without being distracted by everything else.

"Swarm" isn't a formal term. It became popular through OpenAI Swarm, an experimental teaching tool from 2024 built around agents handing work to each other. OpenAI retired it in 2025 and replaced it with the Agents SDK, but the name stuck as shorthand for "lots of agents working together".

🤖 Single agent

One context window, one set of tools, works step by step. Simpler, cheaper and easier to debug. The right choice for most tasks.

🐝 Multi-agent

Several focused agents, often working in parallel. Faster and more thorough on broad tasks, but uses many more tokens and needs coordination.

Why Split the Work?

  • →Parallel work: five research questions can be investigated at once instead of one after another.
  • →Focus: each agent's context only holds what it needs, so long tasks don't drown in detail.
  • →Specialisation: a reviewer agent with read-only tools and a strict checklist is more reliable than asking one agent to "also check your work".
  • →Independent opinions: agents that didn't write something are better at spotting its problems.

The Four Main Patterns

Almost every multi-agent system, whatever the framework, is built from four patterns. Learn these and the frameworks become much easier to understand.

1. Orchestrator–worker

A lead agent plans the work, hands focused pieces to worker agents, and combines what comes back. Workers don't talk to each other; everything goes through the lead.

This is how Anthropic built the Research feature in Claude: a lead agent plans the research and spawns subagents that each search in parallel with their own context, then brings their findings together.

Good forBroad research, checking many files or links at once, any job that splits into independent pieces.
IT example"Review these 40 Intune compliance policies": one worker per policy group, the lead writes a single summary.

2. Handoff (the classic "swarm")

A triage agent works out what's needed and passes the whole conversation to the right specialist, which can hand it on again. Only one agent is in charge at any moment. In the OpenAI Agents SDK, a handoff appears to the model as a tool, for example transfer_to_refund_agent.

Good forConversations where the right expert depends on the question: helpdesks, customer service, internal Q&A bots.
IT exampleA service desk bot that routes "my laptop won't enrol" to a device agent and "I need a licence" to a licensing agent.

3. Sequential pipeline

Agents work in a fixed order, like an assembly line. Each one takes the previous agent's output, does its stage, and passes it on. Adding a reviewer at the end that can send work back gives you a simple quality loop.

Good forRepeatable processes with clear stages: content, reports, change requests, documentation.
IT exampleDraft a change request → assess risk → check against the CAB template → produce the final record.

4. Group chat / team debate

Agents work as peers. They share a task list, message each other directly and challenge each other's conclusions. Claude Code's experimental agent teams feature works this way: teammates claim tasks from a shared list and talk to each other without going through the lead.

Good forReviews from several angles, debugging with competing theories, decisions that benefit from debate.
IT exampleThree agents review a deployment plan: one for security, one for user impact, one for rollback risk.
🧩 Patterns combine. A common design is orchestrator–worker for gathering information in parallel, followed by a short pipeline to write and review the result. The hands-on guide uses exactly this combination.

When to Use One (and When Not To)

Multi-agent systems are not free. Every agent has its own context window, so token use rises with each agent you add. Anthropic found its multi-agent research system used far more tokens than a normal chat, which is only worth it when the task is valuable and splits up well.

Use multi-agent when…Stay with one agent when…
The work splits into independent piecesEach step depends on the one before
The task is broad: lots to search, read or checkThe task is small or routine
You want an independent review or several viewpointsSeveral agents would need to edit the same file
The result is worth the extra costCost or speed matters more than thoroughness

Designing a Good Swarm

1

Give every agent a clear, narrow job

Vague roles cause overlap and gaps. Spell out what each agent does, what it returns and where its job ends. Anthropic's top lesson was giving subagents detailed task boundaries.

2

Pass on the context they need

Agents don't see each other's conversations. Whatever a worker needs to know (the goal, constraints, file names) must be in the instructions it's given.

3

Start small

Three to five agents is plenty for most jobs. More agents means more cost and more coordination, and the gains drop off quickly.

4

One owner per file

Two agents editing the same file will overwrite each other. Split work so each agent owns different files, or keep editing with one agent and let the others only read.

5

Define "done" and a stop condition

Say what a finished result looks like, and limit how long or how many steps agents can take, so a swarm can't loop forever.

Keeping a Swarm Safe

  • 🔒Least privilege per agent: a researcher doesn't need to edit files, and a reviewer should be read-only. Give each agent only the tools its job needs.
  • 📨Treat agent-to-agent messages as untrusted: if one agent reads a malicious web page, a hidden instruction can be passed along to the others. Never let one agent "approve" an action on your behalf.
  • 👤Keep a human checkpoint before anything is sent, published, deleted or deployed.
  • 📋Watch the logs: more agents means more actions to review. Check what each one actually did, not just the final summary.
🛡️ Prompt injection spreads. In a single agent, a poisoned web page affects one agent. In a swarm, the affected agent's output becomes another agent's input. Keep the agents that read untrusted content away from tools that can change things.

Quick Reference: Do's and Don'ts

✅ Do this

  • Start with one agent and add more only when needed
  • Give each agent a narrow role and clear output
  • Run independent work in parallel
  • Make reviewers read-only
  • Keep a human checkpoint before real changes

❌ Avoid this

  • Ten agents where three would do
  • Several agents editing the same file
  • Giving every agent every tool
  • Trusting instructions passed between agents
  • Letting a swarm run with no stop condition
